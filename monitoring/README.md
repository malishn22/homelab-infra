# 📡 Monitoring Stack

This folder contains the full monitoring setup for the homelab, including **Prometheus**, **Grafana**, **Node Exporter**, and **Nginx Exporter for Prometheus**.  
All components run inside Docker and share the `homelab` Docker network so Prometheus can scrape them.

---

## 🧩 Components

### **Prometheus**
Collects metrics from exporters and services.

- Uses configuration from: `prometheus/prometheus.yml`

---

### **Node Exporter**
Gathers system-level host metrics: CPU, memory, filesystems, disk I/O, load average, uptime and
hwmon temperatures. Scraped as job **`node`** (not `node-exporter`) at `node-exporter:9100`.

Dashboard: `grafana/dashboards/host.json`.

Three traps are baked into the dashboard queries — worth knowing before writing new panels:

- **It cannot see the host's network interfaces.** node-exporter runs on the `homelab` bridge,
  and `/proc/net/dev` is generated by the kernel *per network namespace*, resolved from the
  reading process — not from the mount it was reached through. So despite `--path.rootfs=/host`
  it only ever sees its own veth: `node_network_*` contains `eth0` (which is Prometheus scrape
  traffic) and `lo`, never `eno1`/`wlp3s0`/`tailscale0`. Host NIC throughput on the Host
  dashboard therefore comes from cAdvisor's root cgroup instead. CPU, memory, load and diskstats
  *are* host-accurate, because `/proc/stat`, `/proc/meminfo`, `/proc/loadavg` and
  `/proc/diskstats` are not namespaced.
- **Three phantom filesystems.** `node_filesystem_*` reports `/etc/hostname`, `/etc/hosts` and
  `/etc/resolv.conf` — Docker's own injected bind mounts inside the container. They are ext4 like
  `/` and report identical numbers, so an unfiltered disk panel shows the root filesystem four
  times. Filter with `fstype!~"tmpfs|vfat", mountpoint!~"/etc/.*|/run.*"`.
- **Disk devices double-count.** `nvme0n1` is the physical disk and `dm-0`…`dm-5` are the LVM
  logical volumes on top of it. A write to `/var` is recorded on the LV *and* on the backing
  NVMe, so summing both gives exactly 2x the real throughput. Use `device="nvme0n1"` for host
  totals and `device=~"dm-.*"` only for the per-volume breakdown.

- Runs with rootfs access via `--path.rootfs=/host`.

### **Nginx Prometheus Exporter**
Scrapes metrics from the main Nginx reverse proxy (For test purposes).

- Requires `stub_status.conf` enabled inside the nginx container.

---

### **GHMS Backend**
The GHMS (Minecraft manager) backend exposes app-level metrics at `/metrics`
(fleet size, lifecycle events, backups, modpack cache, HTTP stats).

- Scraped over the `homelab` network at `ghms-backend:8000` (job `ghms`).

---

### **cAdvisor**
Exposes per-container resource metrics (CPU, memory, filesystem, network) for everything running
on the host, so container-level usage can be separated from host-level usage. Scraped as job
`cadvisor` at `cadvisor:8080` (no host port — 8080 is taken by calimali).

Dashboards: `grafana/dashboards/containers.json` (per-container, filtered by stack) and
`grafana/dashboards/system-ci.json` (the root cgroup and the systemd slices — the load that is
*not* in a container, chiefly the four CI runners and the Docker daemons).

cAdvisor does not know about "containers" at the kernel level — it walks the **cgroup v2** tree
and emits one series per node, where the `id` label *is* the cgroup path. It sets a `name` label
only for cgroups it recognises as Docker containers. Consequences:

- **`name!=""` is mandatory in every container query.** Of ~64 `container_cpu_usage_seconds_total`
  series only 20 are containers; the other 44 are `/`, `/init.scope` and `/system.slice/*`. The
  root cgroup alone is the whole machine, so an unfiltered `sum` roughly doubles every number.
- **Template variables must not use `label_values(name)`.** The raw `name` label is shared across
  jobs and is polluted with hwmon sensor names, CPU indices, `Debian GNU/Linux`, and GHMS server
  names. Scope it to a cAdvisor metric instead: `label_values(container_last_seen{name!=""}, name)`.
- **GHMS game servers have no Compose labels.** GHMS creates them through the Docker socket, not
  Compose, so `container_label_com_docker_compose_project` is *absent*. An absent label is the
  empty string, which `=~".+"` does not match — so the Stack variable's `allValue` is `".*"`. With
  `".+"` the entire game-server fleet silently vanishes from the dashboard.
- **Counting series is not counting containers.** When a stack is redeployed the replaced
  container keeps reporting under its old cgroup id for up to 5 minutes (Prometheus' lookback
  window), so `count(container_last_seen{name!=""})` over-reports after every CI deploy. Count
  distinct names, or aggregate with `max by (name, ...)`, instead.
- **No usable limits.** Nothing on this host sets a CPU quota, so `container_spec_cpu_quota` does
  not exist at all, and `container_spec_memory_limit_bytes` is `0` for every Compose-managed
  container — only a *running* GHMS game server has a real value (its `ram_mb`, passed through as
  `--memory`). Percent-of-limit panels are therefore impossible; the dashboards express usage as
  a percentage of the host (16 cores / 29.2 GB).

- Reads the Docker socket and `/` (read-only) to discover containers.
- Scraped internally; no host port published.

### **Loki + Promtail**
The log half of the stack, alongside the metrics half.

- **Promtail** tails container logs on the host and ships them to Loki.
- **Loki** indexes them by label and is queried from Grafana as a second datasource, so a spike on
  a metrics dashboard can be pivoted straight to the logs from that moment.
- Both are scraped/served internally; neither publishes a host port.

---

### **Spotify Archiver**
The archiver's web backend exposes app-level metrics (sync runs, run status, durations).

- Scraped over the `homelab` network as job `spotify-archiver`, target `backend:8000`.
- Dashboard: `grafana/dashboards/spotify-archiver.json`.

> ⚠️ That target is the literal container name `backend`, which is generic. Do not name another
> container `backend` on the `homelab` network or Prometheus will scrape the wrong one.

---

### **Health signals**
Three signals exist on every relevant dashboard specifically because their absence is
indistinguishable from good news:

- **`Scrape health`** (all five dashboards) — `min(up{job=~"..."})`, scoped to the jobs that
  dashboard actually queries. If an exporter dies, every panel below goes flat and empty, which
  reads as "nothing is happening" rather than "I have stopped being able to see". `NO DATA` on
  this tile means Grafana cannot reach Prometheus at all.
- **`Container restarts`** (Containers) — `changes(container_start_time_seconds[1h])`. Catches
  crashloops and `docker restart` of the *same* container. A redeploy creates a new cgroup id and
  a fresh series, which is correct: that is a deploy, not an incident.
- **`OOM kills`** (Containers, per container; Host Machine, machine-wide via
  `node_vmstat_oom_kill`). Nothing on this host sets a memory limit, so when memory runs out the
  kernel picks a victim by heuristic — possibly Prometheus rather than whatever leaked. A spike
  here explains an otherwise inexplicable restart.

### **Grafana**
Visualizes data coming from Prometheus and Loki. Datasources and dashboards are both provisioned
from files — see the folder tree below for the four dashboards and `Updating a Dashboard` for how
to change one.

- Accessible in browser on port `3000` by default.
- Admin credentials come from `.env` (`GF_SECURITY_ADMIN_USER` /
  `GF_SECURITY_ADMIN_PASSWORD`) — see `.env.example`.
- The Prometheus datasource **and** dashboards are auto-provisioned from
  `grafana/provisioning/` on startup, so a fresh deploy comes up preconfigured.
  The GHMS dashboard lives in `grafana/dashboards/ghms.json`.

## 📁 Folder Structure

```text
monitoring/
├─ prometheus/
│  └─ prometheus.yml           # Prometheus scrape config
├─ loki/
│  └─ loki-config.yml          # Loki storage + retention config
├─ promtail/
│  └─ promtail-config.yml      # Which container logs to tail and how to label them
├─ grafana/
│  ├─ provisioning/
│  │  ├─ datasources/          # Auto-registered Prometheus + Loki datasources
│  │  └─ dashboards/           # Dashboard provider config
│  └─ dashboards/
│     ├─ containers.json       # Per-container CPU/mem/net/disk + logs, filtered by stack
│     ├─ ghms.json             # GHMS dashboard definition
│     ├─ host.json             # Host CPU/mem/disk/network/load/temps (node-exporter)
│     ├─ spotify-archiver.json # Spotify Archiver sync-health dashboard
│     └─ system-ci.json        # Non-container load: systemd slices, CI runners, bridges
├─ .env.example                # Grafana admin vars (copy to .env)
└─ docker-compose.yml          # Prometheus, Grafana, Node Exporter, Nginx Exporter,
                               # cAdvisor, Loki, Promtail
```

## 🚀 Running the Monitoring Stack

Run inside this folder:

```bash
docker compose up -d
```

This will start:

- Prometheus  
- Grafana  
- Node Exporter  
- Nginx Prometheus Exporter  
- cAdvisor  
- Loki  
- Promtail  

They all join the `homelab` Docker network automatically.

## ✏️ Updating a Dashboard

Provisioned dashboards load from `grafana/dashboards/*.json` on startup — the
JSON file is the source of truth, **not** the Grafana database. UI edits save to
the DB and are **overwritten on the next restart/redeploy**. To make a change
stick:

1. Edit the dashboard in the Grafana UI until it looks right.
2. Dashboard settings (gear) → **JSON Model** → copy the whole model.
3. Paste it over the matching file, e.g. `grafana/dashboards/ghms.json`.
4. Check the panel datasource `uid` is still `prometheus-homelab` (a fresh
   export can revert it to a random value — fix it back, or a clean deploy
   shows "datasource not found").
5. Commit, push, then redeploy / restart Grafana.

## 📝 Notes

- This stack is fully isolated from Linkding.
- Prometheus scrapes everything via container DNS, not via host ports.
- The Grafana datasource and dashboards are auto-provisioned from
  `grafana/provisioning/`. Edit dashboards in git (the JSON), not in the UI —
  provisioned dashboards are marked non-editable in place.
- Copy `.env.example` to `.env` and set a Grafana admin password before first
  run; compose will refuse to start without `GF_SECURITY_ADMIN_PASSWORD`.
- **Prometheus retention is capped deliberately.** The retention flags are enforced against data
  that already exists, not just future growth, and the stricter of time/size wins — so lowering
  either below current usage deletes the oldest blocks on the next start. Doing this once cost
  ~15 days of metrics. Snapshot `monitoring_prometheus-data` before changing them.
- `prometheus-data`, `grafana_storage`, and `loki-data` are **named** volumes, so they live under
  `/var/lib/docker` on a 12 G LVM volume. This stack is the usual reason `/var` fills.
